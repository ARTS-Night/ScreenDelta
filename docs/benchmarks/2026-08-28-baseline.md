# Windows baseline: 2026-08-28

## Environment

- Windows desktop through Windows MCP
- One primary DXGI output: 958 x 925 physical pixels
- Release build, 5-second runs, `try_next_frame(Duration::ZERO)`
- The desktop was mostly static; this is intentionally an unchanged-frame
  baseline, not a full-motion throughput claim.

| Requested FPS | Polls | Captured | Unchanged | Total readback | Mean readback |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 51 | 7 | 44 | 10.396 ms | 1.485 ms |
| 15 | 76 | 7 | 69 | 9.716 ms | 1.388 ms |
| 20 | 101 | 9 | 92 | 11.928 ms | 1.325 ms |
| 30 | 151 | 7 | 144 | 9.762 ms | 1.395 ms |

`acquire_wait` stayed below 2.3 ms in every run because polling used a zero
timeout. Captured counts are desktop updates, not delivered frame targets.

## Interpretation

The current pipeline correctly avoids a CPU readback on DXGI timeout. It does
not yet inspect dirty rectangles for a received DXGI frame, so a desktop update
outside the requested capture region can still cause a full region readback.
The next comparison must use a controlled small-motion and full-motion input;
these baseline numbers must not be presented as throughput at 10–30 FPS.

## Region skip validation after dirty-rect filtering

Windows MCP moved the cursor outside a 120 x 120 capture region during a
five-second, 15 FPS release run. The result was 76 polls, 3 readbacks, 57 DXGI
timeouts, and **16 received updates skipped because their dirty regions did not
intersect the capture region**. Cumulative readback was 0.7839 ms.

This is a controlled proof that region-external desktop damage no longer forces
a crop/readback. It is not a full-motion benchmark.
